# Manco v0.9.9 发布总结

## 阶段目标

本次为常规版本，承接 v0.9.8。落实性能审查清单中用户确认的首批第 1—4 项，减少不必要的数据库读取、远程详情请求和封面解码；同时优化 Bangumi API 缓存与自动刷新，交付此前待发布的 README 通栏圆角品牌图。

遵循先推送代码和标签、再补总结的顺序，不移动已有版本标签。本阶段未宣称完成全部性能审查项目，也不以单项查询基准代替容器内存实测。

## 实际改动

### 首批性能优化

- 修正发现缓存清理时跳过普通 `item.json` 文件的条件，使命名缓存在重启后恢复索引，并正确清理过期目录。
- 本地文件访问目录改用轻量 SQL 投影及下载目录覆盖索引，不再为收集目录反复加载完整任务；封面回退改用作品级封面摘要查询。
- 普通、本地和章节缩略图共用两路生成上限；在读取远程压缩图片前取得额度，合并同图并发请求并写入磁盘缓存。
- 缩略图按小时清理，容量目标约为 2048 个文件、128 MiB、7 天；支持原图回退，远程获取失败不在同次请求内重复重试。
- 发现缓存与订阅缓存封面接口支持 `w` 缩略图参数，探索发现、信息总览、本地仓库和订阅计划同步使用。
- 浏览列表先返回卡片，作者、简介和状态通过有界后台任务补齐；搜索复用同一补全入口。补全只调用作品详情，不额外拉取章节目录。

### Bangumi 缓存与自动刷新

- 热度、连载和新作类栏目默认缓存 6 小时；排名、高分栏目及作品详情默认 24 小时；关键词搜索默认 30 分钟。
- 这是 Manco 的保守刷新策略，不代表 Bangumi 官方存在统一固定更新周期。上游 `Cache-Control` 或 `Expires` 可延长刷新间隔。
- 持久保存响应与验证信息，支持 `ETag`、`Last-Modified` 和 304；过期但保留期内的旧响应立即返回，后台重新验证。
- 同请求合并，上游同时最多两路，待处理请求最多八项；429 遵循 `Retry-After` 全局退避，缺省退避五分钟。
- 只自动刷新最近七天访问过的栏目请求，最多登记 64 个规范请求块，重启可恢复；启动三十秒后开始巡检，此后每轮结束一分钟再巡检。
- 本月和本年新作的日期筛选跨月、跨年自动滚动；服务停止时取消后台请求。
- 以每块 20 条规范化 Bangumi 请求，登录推荐与不同网格分页复用缓存，避免宽屏页大小导致结果遗漏；登录简介补全也复用作品详情缓存。
- 搜索与作品详情按访问刷新，不主动定时遍历。后台刷新不强制替换已打开浏览器页面的内容；页面刷新按钮重新读取后端缓存，缓存仍新鲜时不会强制访问上游。

### 品牌与版本

## 已知限制

- 本机无 Docker CLI，容器镜像由 GitHub Actions 构建验证；尚未在真实 NAS 上记录多任务内存曲线。
- 本机无 gcc，未执行 Go race 检测。
- 独立本地预览进程启动曾被环境策略拦截，未启动新服务，接口行为使用隔离 HTTP 测试验收。
- 未使用真实个人账号触发 Bangumi 限流，也未进行真实 Telegram 通知验收；本阶段不修改 Telegram 交互。
- 自动刷新只维护活跃栏目，不会预抓取所有栏目、搜索词或所有作品详情。
- 后台详情补全受批次和并发限制，源端缺失的字段仍可能保持为空。

## 下一步

在 NAS 验证大量排队任务与少量并发下载时的实际 RSS、封面加载峰值及浏览首屏延迟；观察至少一个 Bangumi 自动刷新周期，核对条件验证、缓存命中和限流退避，再确认后续性能清单的实施范围。
