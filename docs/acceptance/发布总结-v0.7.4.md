# Manco v0.7.4 发布总结

## 阶段目标

本次为常规版本，承接 v0.7.3，完成 Telegram 每日失败重试汇总、订阅计划分页，并继续降低大量排队任务和图片处理带来的内存开销，精简视频下载依赖。

遵循先推送代码和标签、再补总结的顺序，不移动任何已有版本标签。

## 实际改动

### Telegram 重试通知

- 按上海时区自然日、机器人、聊天、内容源和作品分别汇总失败重试。
- 同一作品当天第一次重试发送通知；后续重试发送新的汇总通知，发送成功后删除上一条。
- 最新消息显示当天累计重试次数、章节次和最近三次重试记录；每次最多列出三个章节名，更多内容显示省略数量。
- 本地封面优先，来源封面回退；作者、内容源简称和订阅封面模糊设置继续生效。
- 当天通知索引写入 SQLite 设置，服务重启后可以继续合并；跨天不删除前一天的最终汇总。
- 新消息发送失败时保留旧消息；更换机器人不会误用旧机器人的消息编号。

### Telegram 订阅计划

- 每页 15 条，提供上一页、下一页及当前页码。
- 显示筛选后的总数，跨页编号连续，第一页没有上一页，最后一页没有下一页。
- 保留下载父目录筛选和十分钟无操作自动清理机制。
- 翻页时先发送成功，再移除上一页；限制会话归属，避免跨聊天读取。

### 下载内存

- 队列扫描只查询任务 ID 和内容源，获得全局及来源并发名额后才加载完整任务。
- 到期失败重试与订阅检查重试只读取通知所需摘要，避免反复解析大型章节载荷、简介、标签和合并章节。
- 重试通知不再为每部作品同时启动一个发送协程；单批按作品顺序发送，并使用超时。
- Go 整图解扰改为在请求图片字节前获取限流名额，一次只处理一张，避免等待解扰的协程各自保留大图字节。
- 解码前检查图片尺寸，Go 与 Kototoro 宿主的单图上限为 4000 万像素。
- 下载详情共享缓存由 64 项缩到 8 项。
- Kototoro、Mihon JVM 连续空闲五分钟后停止，下次调用自动启动；活跃请求、重置计时器和旧进程均有保护。
- 插件 JSONL 大响应使用每条消息独立的临时缓冲，避免读过一次大响应后长期保留扩容后的 Scanner 缓冲。
- Kototoro 图片重绘移除无条件整图复制，对未知长度输入限量读取，提前检查像素尺寸，并及时释放位图资源。插件图片仍由原插件运行时签名与解扰。

### 镜像精简

- 保留 Kototoro 和 Mihon 宿主，不删除插件执行能力。
- FFmpeg 改为独立源码构建，只安装 Manco 需要的流复制程序及相关运行库，不把完整系统 FFmpeg 转码依赖链带入最终镜像。
- 固定 FFmpeg n6.1.2 源码及 SHA256，保留网络、代理、TLS、AES-HLS、HLS/DASH 读取、常见媒体探测和 Matroska 输出。
- Docker 构建阶段使用本地生成的 HLS、DASH 夹具进行真实转封装自检；不访问内容源网站。
- 最终镜像包含 FFmpeg 许可证和构建配置。
- 远端完整构建及 HLS/DASH 自检成功；镜像压缩层总量从 v0.7.3 的 187.69 MiB 降到约 144.97 MiB，减少 42.72 MiB，约 22.8%。该数字不等于解压后的本地磁盘占用。

### 发布回归修正

- 首轮 Linux CI 暴露既有轮询测试同时统计命令注册与消息轮询请求的竞争，导致偶发误报。
- 测试改为只统计 `getUpdates`，连续运行 100 次通过；没有改变生产轮询流程。

## 已知限制

- 本机没有 Docker / Linux 构建环境；完整容器编译、HLS/DASH 自检和镜像体积已通过远端 Actions / GHCR 验证。
- 图片超过 4000 万像素时会返回明确错误，防止单张超大图触发不可控解码内存。
- JVM 空闲释放后，下一次插件调用需要重新启动宿主，会有一次启动开销；已安装源和持久化配置不受影响。
- 图片处理、JVM、FFmpeg 和操作系统文件缓存都可能参与容器内存统计，不能把本轮队列基准视为总进程内存保证。
- 未通过真实 Telegram 账号或实际 NAS 下载队列进行端到端测试；通知使用 HTTP 模拟响应验证，不改用户订阅数据。
